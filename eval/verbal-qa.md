# B5-1 구두평가 질문과 답

## Q1. 엑셀과 관계형 DB의 차이는 무엇인가요?

둘 다 표를 다룰 수 있지만 관계형 DB는 테이블 사이 연결과 입력 규칙을 PK·FK·제약조건으로 검사할 수 있다. 이 프로젝트는 메뉴 정보와 좌석 정보를 주문에 복사하지 않고 FK로 연결한다.

## Q2. 현재 테이블과 관계를 설명해 주세요.

테이블은 `menu_categories`, `store_tables`, `menus`, `orders` 네 개다. 관계는 카테고리 1:N 메뉴, 좌석 1:N 주문, 메뉴 1:N 주문으로 세 개다.

## Q3. PK와 FK는 각각 왜 필요한가요?

PK는 한 테이블에서 각 행을 겹치지 않게 식별한다. FK는 다른 테이블의 PK를 가리키며 존재하지 않는 부모 참조를 막는다.

## Q4. SQLite에서 FK를 썼는데도 꼭 확인할 것은 무엇인가요?

SQLite 연결마다 `PRAGMA foreign_keys = ON`을 실행해야 한다. 자동 검증은 PRAGMA 값이 1인지와 없는 좌석 참조가 실제로 실패하는지를 모두 확인한다.

## Q5. INNER JOIN과 LEFT JOIN은 어떻게 다른가요?

INNER JOIN은 양쪽에 연결되는 행만 남긴다. LEFT JOIN은 왼쪽 행을 모두 남기고 오른쪽 연결이 없으면 NULL로 둔다. Query 7은 이 NULL을 이용해 미주문 메뉴 `유자차`를 찾는다.

## Q6. WHERE와 HAVING의 차이는 무엇인가요?

WHERE는 GROUP BY로 묶기 전의 각 행을 거른다. HAVING은 묶고 계산한 결과를 거른다. Query 11은 SERVED 행을 WHERE로 고르고, 판매 수량 합계 3 이상을 HAVING으로 고른다.

## Q7. Query 12에 `IN`을 쓴 이유는 무엇인가요?

현재는 최고가 메뉴가 하나지만 나중에 같은 최고 가격 메뉴가 여러 개일 수 있다. 중간 서브쿼리가 여러 ID를 반환해도 `IN`은 모두 처리한다.

## Q8. Query 13과 14를 어떻게 안전하게 만들었나요?

ID뿐 아니라 예상 현재 상태를 함께 확인한다. 주문 18은 COOKING일 때만 SERVED로 바꾸고, 주문 25는 CANCELLED일 때만 삭제한다. 자동 검증은 영향 행 수가 각각 1인지 확인한다.

## Q9. 어떤 잘못된 값을 DB가 막나요?

PK 중복, 필수값 누락, 카테고리명·좌석 번호 중복, 없는 FK 참조, 음수 가격·수량·좌석·수용 인원, 허용 목록 밖의 주문 상태를 막는다.

## Q10. 인덱스를 왜 만들었나요?

status 조건이 여러 조회에서 반복되므로 `orders(status)`를 후보로 만들었다. 현재 실행 계획은 해당 인덱스를 사용한다. 하지만 데이터 분포와 규모에 따라 달라져 항상 빨라진다고 단정하지 않는다.

## Q11. JOIN과 서브쿼리 결과가 같다는 것을 어떻게 확인했나요?

같은 시간대 메뉴 질문을 JOIN과 서브쿼리로 실행하고 두 결과의 모든 `(id, name, price)` 값을 정렬해 비교했다. 둘 다 같은 5행이라 PASS다. JOIN에는 중복 제거를 위해 DISTINCT를 사용했다.

## Q12. KPI의 계산 단위에서 주의할 점은 무엇인가요?

현재 `orders` 한 행은 주문서 전체가 아니라 메뉴 한 항목이다. 따라서 주방 혼잡도 20.8%는 주문서 수 비율이 아니라 주문 항목 행 중 COOKING 비율이다. 좌석 평균은 물리 좌석 ID별 매출을 먼저 계산해 중복 가중을 피했다.

## Q13. 자동 검증과 외부 동료평가는 같은가요?

아니다. 자동 검증은 코드가 정한 조건의 PASS다. 외부 동료평가는 다른 사람이 직접 실행하고 설명을 듣고 의견을 남기는 절차다. 외부 평가 전에는 결과를 대기로 표시한다.
