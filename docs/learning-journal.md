## 단계별 학습 확인

### 1단계 — 엑셀과 데이터베이스

처음 이해한 문장:

> 엑셀도 표를 만들 수 있지만, 관계형 DB는 여러 표 사이의 연결과 규칙을 DB가 검사하게 할 수 있다.

직접 확인한 것:

- 메뉴·좌석·주문을 한 표에 모두 복사하지 않았다.
- 주문에는 `table_id`와 `menu_id`를 저장했다.
- 존재하지 않는 좌석 ID를 넣자 FK 오류가 발생했다.

### 2단계 — PK, FK, 1:N

- PK는 행마다 겹치지 않는 신분증이다.
- FK는 다른 표의 신분증을 가리키는 연결 번호다.
- 카테고리 하나에 메뉴 여러 개가 연결되므로 1:N이다.
- 좌석 하나와 메뉴 하나에도 주문 여러 개가 연결될 수 있다.

확인 결과: PK 4개, FK 3개, 1:N 관계 3개.

### 3단계 — SQLite의 주의점

배운 것:

1. SQLite는 파일 하나로 시작할 수 있어 입문 실습에 알맞다.
2. FK는 연결마다 `PRAGMA foreign_keys = ON`으로 켠다.
3. SQLite에는 별도 DATETIME 저장 클래스가 없다.
4. 이 프로젝트는 시간을 `YYYY-MM-DD HH:MM:SS` 형식으로 통일한다.

실험:

- FK ON 상태에서 없는 좌석 9999를 참조한 주문 입력 → 차단 PASS

### 4단계 — INSERT 순서

부모가 먼저 있어야 자식 FK가 부모를 찾을 수 있다.

```text
menu_categories, store_tables → menus → orders
```

확인 결과: 10/12/16/25행을 새 DB에 넣었다.

### 5단계 — 기본 조회

- `WHERE`: 필요한 행을 고른다.
- `ORDER BY`: 순서를 정한다.
- `LIMIT`: 보여 줄 행 수를 제한한다.
- `LIKE`: 글자 일부가 포함됐는지 찾는다.

Query 1~4를 각각 실행해 4/2/5/3행을 확인했다.

### 6단계 — JOIN

- INNER JOIN: 양쪽에 연결된 행만 남긴다.
- LEFT JOIN: 왼쪽은 모두 남긴다.
- `WHERE 오른쪽.id IS NULL`: 연결되지 않은 왼쪽 행을 찾을 수 있다.

Query 7에서 유자차 1개, Query 8에서 미주문 좌석 3개를 확인했다.

### 7단계 — 집계

- COUNT: 개수를 센다.
- SUM: 합계를 구한다.
- AVG: 평균을 구한다.
- GROUP BY: 같은 기준끼리 묶는다.
- HAVING: 묶은 뒤의 결과를 거른다.

Query 9~11을 실행해 카테고리, 좌석, 판매 메뉴 기준 집계를 확인했다.

### 8단계 — 서브쿼리와 안전한 변경

- 서브쿼리는 SQL 안에 들어가는 작은 SQL이다.
- 최고 가격을 먼저 찾고 그 가격의 메뉴 ID를 찾아 주문을 조회했다.
- UPDATE/DELETE는 ID뿐 아니라 현재 상태까지 확인해야 실수를 줄일 수 있다.

실증:

- Q13: `id=18 AND status='COOKING'` → 1행 변경
- Q14: `id=25 AND status='CANCELLED'` → 1행 삭제

### 9단계 — 인덱스

책의 찾아보기처럼 자주 찾는 기준에 별도 길을 만든다고 이해했다.

- 만든 인덱스: `idx_order_status ON orders(status)`
- 만든 이유: `status`로 자르는 조회(Q03, 보너스 B01·B02)가 반복되고, 주문은 읽기가 쓰기보다 많은 테이블이다.
- 현재 실행 계획: `SEARCH orders USING INDEX idx_order_status (status=?)`
- 주의 1: 인덱스를 "만들었다"와 "빨라졌다"는 다른 주장이다. 25행에서는 시간이 체감되지 않아 앞의 사실만 기록한다.
- 주의 2: `status`는 허용값이 3개라 선택도가 낮다. 행이 많아지면 SQLite가 인덱스를 무시할 수 있고, 그때는 `orders(status, order_time)` 복합 인덱스가 더 나은 후보다.
- 주의 3: 인덱스도 저장 공간과 쓰기 비용을 요구한다. Q15 다음에 실행되는 보너스 계획에 인덱스가 나타나는지까지 함께 확인했다.

### 10단계 — 설명 대신 재현

한 번 실행한 화면을 믿는 대신 다음 흐름을 자동화했다.

```text
새 DB 파일 → 스키마 → seed → Q1~Q15(UPDATE·DELETE 포함) → 보너스·KPI → 무결성 위반 실험 → 텍스트 증거 → 실행 결과 캡처 이미지
```

README가 안내하는 sqlite3 CLI 순서와 일부러 같은 흐름이다. 순서가 갈라지면 문서의 숫자와 채점자가 눈으로 확인하는 숫자가 갈라지기 때문이다. 검증은 SQL뿐 아니라 문서도 본다 — 보고서가 인용한 SQL이 실제 파일과 다르고, README의 Query 설명이 SQL 주석과 다르고, markdown 링크가 끊기면 PASS가 나오지 않는다.

최종 결과: `B5-1 AUTOMATED VERIFICATION: ALL PASS`.

## 학습 멘토 역할과의 문답

> 아래는 개념을 스스로 점검하기 위한 **학습 멘토 가상 문답**이다. 핵심 개념의 오해하기 쉬운 지점들을 점검한다.

### 문답 1 — FK만 있으면 모든 잘못된 값을 막나요?

- 학생: FK를 만들었으니 수량 -1도 막히나요?
- 학습 멘토: 아니다. FK는 “부모 행이 존재하는가”를 검사한다. 수량 범위는 CHECK가 담당한다.
- 적용: `CHECK (quantity > 0)`을 추가하고 음수 입력 차단을 검사했다.

### 문답 2 — LEFT JOIN을 썼는데 왜 미주문 행이 안 보이나요?

- 학생: SQL은 맞는 것 같은데 미주문 메뉴 결과가 0행입니다.
- 학습 멘토: 정말 미주문인 seed가 있는지 먼저 확인해야 한다. 쿼리 구조만으로 결과가 생기지는 않는다.
- 적용: 주문에서 참조하지 않는 유자차를 넣어 Q7이 1행을 반환하게 했다.

### 문답 3 — JOIN이 서브쿼리보다 무조건 빠른가요?

- 학생: JOIN이 항상 더 빠르다고 써도 되나요?
- 학습 멘토: 데이터, 인덱스, DB 실행 계획에 따라 다르다. 같은 결과인지와 현재 계획을 먼저 확인한다.
- 적용: 두 결과의 모든 행을 비교하고 `EXPLAIN QUERY PLAN`을 저장했다.

### 문답 4 — UPDATE에서 ID가 있으면 충분한가요?

- 학생: 주문 ID 18만 쓰면 한 행만 바뀌니 안전하지 않나요?
- 학습 멘토: 다른 사람이 이미 상태를 바꿨을 수 있다. 예상 현재 상태도 조건에 넣으면 의도한 전이만 허용할 수 있다.
- 적용: `id=18 AND status='COOKING'` 조건을 사용했다. 이 가드 때문에 Q13 이후 보너스 KPI의 숫자가 바뀐다(5행 → 4행, 20.8% → 16.7%).

### 문답 5 — 주문에도 메뉴명을 저장하면 편하지 않나요?

- 학생: `orders`에 `menu_name`과 가격을 같이 넣으면 JOIN을 안 해도 되는데 왜 FK만 쓰나요?
- 학습 멘토: 이름은 복사를 안 하는 게 맞다. 다만 금액은 예외다. 주문 시점 금액을 부모 테이블에만 두면 가격을 수정했을 때 과거 매출이 조용히 다시 계산된다.
- 적용: 이번 범위에서는 `menu_id` 참조만 유지하고, 그 대가로 KPI가 "현재 가격 기준"임을 `bonus_report.md` §6과 `decision-log.md` D11에 명시했다. 확장 항목은 `orders.unit_price` 스냅샷이다.

### 문답 6 — `id`가 있는데 왜 좌석 번호를 또 저장하나요?

- 학생: `table_number`는 `id`와 같으니 redundant하지 않나요?
- 학습 멘토: 값이 같으면 중복처럼 보이지만 역할이 다르다. `id`는 FK가 참조하는 내부 키라 바뀌면 안 되고, `table_number`는 매장 사정(이름표 변경, 층 이동)으로 바뀔 수 있는 자연키다.
- 적용: 1층 `1xx`·2층 `2xx`로 서로 다른 값을 넣어 두 키를 데이터로 분리했다. 그래서 `ORDER BY id`와 `ORDER BY table_number`의 결과가 달라진다.
