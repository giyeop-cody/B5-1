# 구현 선택과 트레이드오프 기록

## D1. DBMS 선택

| 선택지 | 장점 | 단점 |
|---|---|---|
| SQLite | 서버 없이 파일/메모리로 바로 실행, Python 기본 모듈 지원 | 타입과 FK 활성화 방식이 다른 DB와 다름 |
| MySQL/PostgreSQL | 운영 서비스에서 많이 사용, 기능이 풍부 | 서버 설치·실행이 필요해 입문 재현이 무거움 |

**결정:** 공식 가이드의 입문 추천과 로컬 재현성을 따라 SQLite를 사용한다. SQLite 차이는 SQL 주석과 문서에 밝힌다.

## D2. 주문 데이터 모델

| 선택지 | 장점 | 단점 |
|---|---|---|
| 현재처럼 주문 메뉴 한 항목을 `orders` 한 행으로 저장 | 4-table 과제 범위에서 단순함 | 한 결제에 여러 항목을 묶는 주문 헤더가 없음 |
| `orders` + `order_items`로 분리 | 실제 주문서와 항목을 자연스럽게 표현 | 테이블·쿼리·상태 관리가 늘어남 |

**결정:** B5-1에서는 기존 4-table 구조를 유지한다. 지표 이름에는 “주문 항목 행”의 뜻을 명확히 쓴다. 확장은 설계서에만 기록한다.

## D3. 주문 시각 저장

| 선택지 | 장점 | 단점 |
|---|---|---|
| ISO 형식 TEXT | 사람이 읽기 쉽고 같은 형식이면 정렬 가능 | 형식이 섞이면 비교가 깨짐 |
| Unix epoch INTEGER | 계산과 비교가 일정함 | 사람이 바로 읽기 어려움 |

**결정:** 기존 데이터와 입문 가독성을 위해 `YYYY-MM-DD HH:MM:SS`를 쓴다. SQLite의 DATETIME은 별도 저장 클래스가 아니라 선언 의도임을 기록한다.

## D4. 값 범위 강제 위치

| 선택지 | 장점 | 단점 |
|---|---|---|
| 문서와 INSERT 작성자만 믿음 | DDL이 짧음 | 실수한 값이 그대로 저장됨 |
| DDL CHECK 사용 | DB 자체가 잘못된 값을 차단 | 허용 규칙 변경 때 스키마 수정 필요 |

**결정:** 가격·좌석 번호·수용 인원·수량·주문 상태에 CHECK를 둔다. 이번 프로젝트는 DB 자체 무결성 학습이 목적이다.

## D5. Q7 LEFT JOIN 검증용 데이터

| 선택지 | 장점 | 단점 |
|---|---|---|
| 기존 15개 메뉴만 유지 | 데이터 변경 없음 | 모두 주문되어 미매칭 결과가 0행 |
| 미주문 메뉴 1개 추가 | LEFT JOIN의 NULL 행을 눈으로 확인 | 메뉴 수가 16개로 늘어 기존 결과 재생성 필요 |

**결정:** `유자차`를 추가하고 모든 결과를 같은 새 DB에서 다시 만든다.

## D6. UPDATE/DELETE 조건

| 선택지 | 장점 | 단점 |
|---|---|---|
| ID만 조건 | 짧고 단순함 | 예상하지 않은 현재 상태도 변경 가능 |
| ID와 현재 상태 조건 | 허용한 상태 전이만 실행 | 조건이 맞지 않으면 0행이므로 결과 확인 필요 |

**결정:** ID와 현재 상태를 함께 사용하고 영향 행 수가 정확히 1인지 자동 검증한다.

## D7. JOIN/서브쿼리 비교 방법

| 선택지 | 장점 | 단점 |
|---|---|---|
| 반환 행 수만 비교 | 간단함 | 값이 달라도 행 수가 같을 수 있음 |
| 정렬된 전체 튜플 비교 | 실제 결과 동치를 확인 | 비교 코드가 조금 더 필요 |

**결정:** 전체 행 값을 비교한다. 성능은 현재 `EXPLAIN QUERY PLAN`을 기록하는 범위로 제한하고 보편적 우위를 주장하지 않는다.

## D8. 좌석 KPI 평균 계산

| 선택지 | 장점 | 단점 |
|---|---|---|
| 주문 행을 바로 capacity로 GROUP BY | SQL이 짧음 | 주문 많은 좌석이 중복 가중될 수 있음 |
| 좌석 ID별 매출 후 capacity별 평균 | 물리 테이블 하나가 평균에서 한 번 반영 | CTE가 추가됨 |

**결정:** 두 단계 계산을 사용해 “물리 테이블당 평균 매출”이라는 지표 이름과 계산 단위를 맞춘다.

## D9. 증거 생성

| 선택지 | 장점 | 단점 |
|---|---|---|
| 사람이 GUI에서 개별 캡처 | 실제 DB 도구 화면을 그대로 보여 줌 | SQL 변경 뒤 누락·혼합이 생기기 쉬움 |
| 한 자동 실행에서 텍스트와 PNG 생성 | 반복 가능하고 SQL/결과 출처가 같음 | 생성 스크립트와 Pillow가 필요 |

**결정:** 자동 실행을 기준 증거로 삼는다. 텍스트에는 SQL·결과·검증 메모를 넣고 PNG는 같은 텍스트로 만든다.

## D10. 외부 동료평가

| 선택지 | 장점 | 단점 |
|---|---|---|
| 구현자가 예상 평가를 채움 | 문서가 즉시 완성된 것처럼 보임 | 실제 외부 검토가 아니며 신뢰할 수 없음 |
| 빈 양식과 대기 상태를 남김 | 평가 출처가 정직하고 추적 가능 | 외부 평가 전에는 결과가 비어 있음 |

**결정:** 요청서와 체크리스트만 준비한다. 평가자·일시·의견은 실제 평가자가 확인한 후 기록한다.
